# Airtable P0–P2 acceptance evidence

Date: 2026-10-10. Scope here is foundation F only. Local managed worktree; no push, deployment, release tag or published image. Other subprojects are not claimed complete.

## Foundation: implemented and isolated PostgreSQL verified

- Shared `writeCellInTransaction` preserves reference/ownership validation, record-before-cell lock order, history and overwrite hints; nullable actors propagate to expression history. `recompute:false` lets batch writes materialize once after each row.
- Protected `record.writeBatch` requires editor membership. It validates table ownership even for empty cell maps, rejects duplicate records and direct expression writes, and locks existing records and fields in stable order. Returned record IDs follow input order.
- Server budgets: 100 rows, 500 cells, 1 MiB UTF-8 serialized batch, 256 KiB serialized cell, transaction-local 30-second statement timeout. Multi-byte budget cases are exercised.
- Retry receipts share the data transaction, use `(actorKey, requestId)` and SHA256 of the body with sorted cell keys. Identical concurrent requests replay; changed bodies conflict. Actor-local cleanup uses a materialized candidate set capped at 100 expired rows and preserves seven-day live receipts. Cleanup is opportunistic, not a periodic worker.
- REST partial-success `cellErrors` implementation is unchanged; existing records-service and route regressions pass in the full suite. Client paste, public Forms, Kanban and integration enhancements remain subsequent work. The API retry documentation states that clients must reconcile instead of retrying after seven days.

PG coverage includes whole-batch rollback, receipt replay/collision, canonical cell key order, empty row creation, row/cell/UTF-8 budgets, viewer denial, wrong-table IDs including empty cells, duplicate IDs, expressions, nullable record/history attribution, transaction-helper validation and rollback, bounded actor-specific receipt cleanup, and concurrency between actual public `record.writeBatch` and `cell.upsert` calls. The public API race queues both writers behind a controlled record lock, observes the PostgreSQL blocking chain (refreshing the statistics snapshot), then verifies final value and ordered history. It does not substitute an internal batch simulation for the API race.

An intermediate combined PG run found that the original DELETE subquery could rescan and delete 101 old receipts. The materialized CTE fix passed the same max-100 assertion. The initial concurrency observer also required `pg_stat_clear_snapshot` to see newly connected writers inside its transaction; the final observer and API test pass.

The normal suite deliberately skips opt-in PG tests; those skips are not presented as acceptance. The separate foundation PG invocation above is the acceptance evidence. Live Airtable validation, upgrade/restore rehearsal and later P0–P2 feature gates have not run as part of foundation.
