### Important (Should Fix)

**FR-1 [P2] — Final-attempt leases can become permanently pending after lifecycle changes.**

- Location: `apps/web/src/server/trpc/routers/webhook.ts:55-65`; related `apps/web/src/server/webhooks/worker.ts:59-78` and the dead-only retry gate at `webhook.ts:214`.
- A fifth claim increments `attempts` to 5. Pause, rotation, or explicit resume then calls `invalidateLeases`, changing the lease to `pending` without changing attempts. Its old acknowledgement correctly fails the token/state guard. The worker only selects attempts below 5, while its exhausted-lease sweep only handles `leased`; this pending row is therefore never sent, never marked dead, never cleaned, and cannot be manually retried. It permanently consumes queue capacity. This does not depend on a network race beyond invoking a permitted management action while a final attempt is in flight.
- Preserve the five-attempt ceiling and stale-ACK protection, but move exhausted invalidated leases to `dead` (or provide an equivalent explicit exhausted-pending reconciliation). Leave lower-attempt rows pending. Manual retry can then reset attempts under the existing owner/capacity gate. Do not reset all automatic attempt budgets on rotation silently.
- Smallest regression: seed one event at attempts 4; claim to get a real fifth lease; rotate; verify the old ACK is rejected and the event reaches a recoverable terminal state; invoke owner retry and deliver once with an injected transport using the new secret and same event ID. Parameterize the shared invalidator for pause/resume, retaining an attempts-1 case to prove ordinary leases still resume. Existing lifecycle tests only rotate/pause at attempts 1/2; the exhaustion test only covers expired `leased` rows.
- **Plan boundary conflict requiring an explicit controller ruling:** integration task 6, Edit 1 literally says rotation clears leased rows back to pending. Task 5, Edit 1 and spec I4 simultaneously impose five attempts and terminal exhaustion. The literal unconditional pending rule is incomplete at attempt 5. Adopting a dead-at-exhaustion exception resolves that plan inconsistency without expanding scope.

**FR-2 [P2] — Rapid filter edits persist stale operators and can leave rows/counts behind the saved filter.**

- Location: `apps/web/src/components/view-config/filter-panel.tsx:120-122`; consumer `apps/web/src/app/bases/[baseId]/tables/[tableId]/grid-editor.tsx:826-830`, with shared completion bookkeeping at `:425-443`.
- `FilterPanel` derives every patch from the last server-supplied conditions, and Grid sends a whole options replacement without a local draft or serialized write queue. Starting at `equals 1`, select `gte`, then type `90` before the view query refresh: the second request is `equals 90`, so the selected comparison is lost. This matches the independently recorded browser observation; it is not explained away by an automation wait. Concurrent completions also share one `pendingOptionKeysRef` set: the first success clears it, so the last row-affecting success may not invalidate records/counts for the final saved options.
- Keep a view-scoped local options draft as the source of subsequent edits and serialize/coalesce writes, or prevent dependent editing until the authoritative update and refetch settle. Associate invalidation with each committed request, not a set cleared by unrelated completions. Preserve nested-filter read-only behavior and cancel ownership on view changes.
- Smallest regression: hold the first mutation/refetch unresolved, choose `gte`, change the operand, then settle controlled promises. Verify the final persisted options retain both `gte` and the new operand, and the last committed filter causes row/count refresh. Cover an overlapping UI-only option change so a width/hidden-field save cannot restore an old filter. The existing filter test mocks Select and asserts only a single isolated `onChange` call, which cannot catch this path.
- This updates an inherited server-prop editing pattern now exercised by G4 and explicitly parked for whole-branch triage; it is not claimed to originate solely in the new operator definitions.

**FR-3 [P2] — Public Form retries lack the seven-day client safety boundary.**

- Location: `apps/web/src/components/forms/public-form.tsx:22-23,31-55`; related `apps/web/src/server/forms/submission.ts:129-174` and the existing regression at `submission.pg.test.ts:373`.
- The page retains only the frozen request body, with no first-attempt timestamp. After an uncertain accepted submission, an owner can delete the record (cascading its audit), and the page can remain open beyond the receipt's seven-day window while its default 30-day publication remains valid. Clicking ordinary **Retry** then reuses the old UUID. With both audit and active receipt absent, the server intentionally creates a new tracked record. The existing PG test explicitly verifies this behavior. Thus the UI silently performs a fresh submission where F3 requires expired retries to stop and the user to confirm a new submission.
- Store a first-attempt timestamp with the frozen body. At or beyond seven days, do not send that body on ordinary Retry; show the uncertainty warning and require the existing explicit **Confirm new submission** flow with a fresh UUID. Reset the timestamp only for a genuinely new confirmed request, not every retry. Grid already implements the comparable retention guard.
- Smallest regression: uncertain response, advance the clock just before seven days and prove byte-identical retry; advance to the boundary and click Retry, prove no fetch occurs and confirmation is required; confirm and prove the UUID changes. The server's deleted-audit/expired-receipt test can remain: the gap is in the client promise, and no unlimited server receipt retention is requested.
- This respects both ledger rulings: audits remain until record/publication cascade, and active receipts acknowledge historical acceptance after deletion. Neither ruling authorizes the UI to treat an expired receipt as a safe replay.

## Root cause and evidence

The failed production container stop is recorded in `/private/tmp/markpocket-final-validation-hBfAzO/graceful-stop.log`: SIGTERM entered graceful shutdown, the eight-second fallback fired, and the container exited 1 with OOM false.

Production awaited both webhook stop and the HTTP server close callback before calling the realtime gateway's `closeAll`. An upgraded WebSocket remains an active server connection: stopping the listener does not complete the HTTP close callback until that connection closes. The code responsible for closing it was unreachable behind that callback.

A standalone Node 24.14.0 fixture with the installed ws package reproduced the dependency using an ephemeral localhost port. With one connected WS client, 100 ms after `server.close()`: `listening=false`, `drained=false`, `webSocketClients=1`.
