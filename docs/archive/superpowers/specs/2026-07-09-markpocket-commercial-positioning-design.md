## 1. 产品定位与品牌叙事

### 一句话定位

> **Markpocket —— 你可以自己掌控数据的 Airtable，插件拓展一切。**

### 三层叙事

| 受众 | 说辞 |
|---|---|
| **技术决策者（CIO/CTO）** | "自托管数据库，不锁数据、不膨胀、不 SaaS 绑架。插件系统让你只装需要的功能，不给全家桶付钱。" |
| **最终用户（小团队）** | "像 Airtable 一样好用，但数据在你服务器上。需要什么功能就去装个插件，就像装 App 一样。" |
| **第三方开发者** | "在 markpocket 上发布插件，触达自托管数据库的用户群体。70% 收入归你，平台处理支付和分发。" |

### 核心差异化

| 产品 | 模式 |
|---|---|
| Airtable | SaaS + 订阅制全家桶 |
| NocoDB | 开源 + 界面对 Airtable |
| Baserow | 开源 + 云托管 |
| **markpocket** | **开源 + 自托管 + 插件市场 = 你对数据的绝对控制 + 你选择功能的自由** |

### 品牌修辞

> "Notion 的数据库 + Obsidian 的插件生态，但全部自托管。"

## 2. 插件系统架构概要

### 三层结构

```
┌──────────────────────────────────────────────┐
│               插件市场（Marketplace）           │
│  发现插件 · 购买/下载 · 评分 · 版本管理        │
├──────────────────────────────────────────────┤
│               插件运行时（Plugin Runtime）      │
│  SDK 加载 · 生命周期管理 · 权限沙箱 · 资源隔离  │
├──────────────────────────────────────────────┤
│           开源核心（AGPL v3 核心）              │
│  Base/Table/Field/Record/View + 插件注册接口   │
└──────────────────────────────────────────────┘
```

### Plugin API 扩展点

SDK 提供给第三方开发者的能力：

| 扩展点 | 说明 | 示例插件 |
|---|---|---|
| **Field Type** | 注册新的字段类型 | JSON Field、Rating、QR Code |
| **View Type** | 注册新的视图类型 | Calendar、Gantt、Timeline |
| **Table Action** | 数据变更时触发的操作 | Webhook、Slack 通知 |
| **UI Slot** | Topbar 按钮、侧栏面板、右键菜单 | 导出按钮、数据透视 |
| **Server Router** | 注册 tRPC router，联动前后端 | 第三方数据同步 |
| **Storage Provider** | 注册新的存储后端 | S3、MinIO、WebDAV |
| **Auth Provider** | 注册新的 SSO/OAuth | GitLab、Azure AD、Okta |

### 收费插件技术闭环

1. 插件打包为 npm package + manifest（含`price`、`license`元信息）
2. 用户通过 Marketpace 购买，Stripe/Paddle 完成支付
3. 平台生成 license key（绑定实例机器指纹）
4. 插件运行时在加载插件时验证 license（支持在线 + 离线容灾）
5. 验证通过后加载插件代码
6. 插件更新时重新验证

## 3. 定价与许可模型

### 三层定价体系

```
┌────────────────────────────────────────────────────────────┐
│  🆓 开源核心 — 免费（AGPL v3）                              │
│  ├── v1 全部功能（Base/Table/Field/Record/Grid/Form/...）   │
│  ├── 基础 Field Type 插件 + 所有免费插件                     │
│  ├── 自托管（单容器）                                       │
│  └── 社区支持（GitHub Issues + Discord）                    │
├────────────────────────────────────────────────────────────┤
│  🔌 付费插件 — 按个买（$5–$49/插件，per-instance per-year）  │
│  ├── 第三方开发者上架，平台抽 30%                            │
│  ├── 第一方插件收入 100% 归项目所有者                        │
│  ├── License key 验证（离线/在线均可）                       │
│  ├── 30 天退款保证                                          │
│  └── 版本更新在 license 有效期内免费                         │
├────────────────────────────────────────────────────────────┤
│  💼 Business License — 年付（$999+/年）                      │
│  ├── 付费插件池全部可用（每年可选 5 个插件）                 │
│  ├── 优先技术支持 + 私信频道                                 │
│  ├── 可选品牌定制（White Label）                             │
│  └── 合规文件（SOC2 报告 / 数据处理协议）                     │
└────────────────────────────────────────────────────────────┘
```

### 关键设计决策

| 决策 | 理由 |
|---|---|
| **不按用户数收费** | 与"小团队极简"定位一致；用户数不是一个自然的价值捕捉维度 |
| **per-instance per-year** | License key 绑定实例机器指纹；续费制，避免一次性买断后无持续收入 |
| **Business 命名，而非 Enterprise** | "Business" 定位给中型企业一站式打包；真正的 Enterprise 功能可以做成独立付费插件 |
| **商业许可不涉及核心开源代码** | 插件 license 验证模块可以闭源，其余核心功能保持 AGPL 完整 |

## 4. 付费插件清单（第一批）

### 第一方付费插件

以下为冷启动阶段由项目所有者亲自开发的插件，按优先级排序：

| 插件 | 目标价（年） | 开发周期 | 理由 |
|---|---|---|---|
| **S3 / 对象存储附件** | $19 | 2 周 | 生产环境刚需；`StorageProvider` 接缝已落地（ADR-0006），实现 `put/get/remove` 即可接入 |
| **Excel 导入导出** | $15 | 2 周 | CSV 不够用，几乎每个用户都会碰到 |
| **Webhook / 自动化** | $29 | 3 周 | 集成企业微信/Slack/飞书，B 端视觉价值高 |
| **Calendar 视图** | $15 | 3 周 | 有可视化感知，"看到效果"驱动付费；View Type 扩展点示范 |
| **OIDC SSO** | $29 | 1 周 | 公司统一账号登录的需求明确；Auth Provider 扩展点示范 |

### 免费插件（第一方，用于生态铺垫）

| 插件 | 理由 |
|---|---|
| **Rating Field** | 简单的 Field Type 示范，SDK 开发者参考 |
| **QR/Barcode Field** | 实用 + 展示 Field Type 能力的低开发量案例 |
| **JSON Field** | 开发者场景刚需，但模式简单 |

## 5. 插件市场冷启动策略

### Phase 0 — 市场基础设施（你一个人做）

| 里程碑 | 内容 |
|---|---|
| **Plugin SDK v1** | 发布 TypeScript Plugin API + 文档 + 示例项目 |
| **Marketplace 页面** | 简单的插件目录（Grid 列表 + 搜索 + 分类） |
| **支付与许可** | Stripe/Paddle 集成 + license 生成与验证 API |
| **2–3 个第一方付费插件** | 你亲自写第一批插件，验证 SDK 可用的同时证明有人愿意付钱 |

### Phase 1 — 社区激活

- 开源 1–2 个插件的源码作为参考（AGPL v3），降低第三方开发的心理门槛
- 发布 SDK 文档 + 快速入门（从创建到上架 30 分钟）
- 开放插件审核机制（初期手动审核，量大了自动化）
- **零抽成启动期**：前 6 个月平台不抽成，加速插件库扩充

### Phase 2 — 飞轮启动

- 插件数量达到 50+ 时，激活 30% 抽成
- 推出 Featured / Trending 排名
- 对月销超过 $1,000 的开发者提供推广支持（社交媒体曝光、官方博客采访）
- 引入"Verified 开发者"徽章机制

## 6. 实施路线图

以 solo dev 节奏估算。每个 Phase 完成后可以 pause 验证后再继续。

### Phase 0 — 核心解耦（~2 个月）

_目标：开源核心拆出 Plugin API 扩展点，让第一个插件跑通_

- 重构 `apps/web`，识别 Plugin API 扩展点
- 定义 Plugin 接口（field type / view type / ui slot / server router）
- 实现最小插件加载器（声明式配置 + tRPC 动态路由注册）
- 交付：SDK v1 alpha + 1 个示例插件

### Phase 1 — 市场基础设施（~1 个月）

_目标：用户可浏览、购买、安装插件_

- Marketplace 前端页面（插件目录 + 详情页 + 已购管理）
- Stripe/Paddle 支付集成
- License key 系统（生成 + 在线验证 + 离线容灾）
- CLI 工具（`markpocket plugin create` / `publish` / `install`）
- 交付：完整的上架→购买→安装链路

### Phase 2 — 第一批付费插件（~1 个月）

_目标：第一批付费用户产生收入_

- 开发 3 个付费插件（S3 + Webhook + Excel）
- 开发 2 个免费示例插件（Rating + JSON Field）
- 内部使用至少一周，打磨开发者体验
- 交付：可公开上架的插件 + 文档

### Phase 3 — 社区开放（持续）

_目标：第三方开发者生态起步_

- SDK 正式文档 + Quickstart + 示例项目
- 插件审核流程上线（手动 + Lint 自动检查）
- 零抽成启动期开始（6 个月倒计时）
- 在 GitHub / X / Hacker News 宣传插件市场

## 7. 风险与应对

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| **AGPL v3 不能完全阻止插件盗版** | 高 | 中 | License 验证模块闭源；核心保持开源完整；为信任付费的用户提供 Business License（白标 + 合规） |
| **第三方插件质量参差，影响品牌** | 高 | 中 | 人工审核上架（Phase 3）；"Verified" 徽章 + 评分系统；存在安全问题的插件立即下架 |
| **插件市场冷启动失败（没人开发、没人买）** | 中 | 高 | 第一方插件先跑通支付流程；零抽成 6 个月；主动联系开源社区开发者；核心 + 插件 SDK 必须有"我自己想用"的体验 |
| **solo dev 维护 SDK + 核心 + 市场 + 支持** | 高 | 高 | 优先做低复杂度的插件（避免自动化引擎等大工程）；复用 Stripe/Paddle 的现成能力；审核手动控制节奏；不承诺 SLA |
| **支付与税务合规** | 低 | 中 | 初期用 Paddle（他们处理 VAT/Sales Tax）；手动发票也可行；复杂后转专业 CPO |

## 附录 A：术语表

| 术语 | 定义 |
|---|---|
| **开源核心** | markpocket 的 AGPL v3 核心仓库，包含所有 v1 功能和 Plugin API |
| **Plugin SDK** | 面向第三方开发者的 TypeScript 库，定义扩展点接口 |
| **Marketplace** | 插件目录网站，支持浏览/搜索/购买/安装 |
| **License Key** | 购买付费插件后获得的许可码，绑定实例 |
| **Business License** | 企业年付许可，包含付费插件池 + 支持 + 白标 |
| **Extension Point** | SDK 定义的插件注册入口（Field Type / View Type / UI Slot / Server Router 等） |

## 附录 B：与现有 ADR 的兼容性

| ADR | 兼容性 | 说明 |
|---|---|---|
| **ADR-0001**（<10 万行设计目标） | ✅ | 插件不影响此约束；付费插件不改变行数上限 |
| **ADR-0002**（LWW + 软实时） | ✅ | 插件可监听但不能修改数据同步策略 |
| **ADR-0003**（Expression Field） | ✅ | 插件不可修改 Expression 的求值语义 |
| **ADR-0004**（单租户自托管） | ✅ | 插件不能引入多租户；Business License 不改变架构 |
| **ADR-0005**（row-per-cell + JSONB） | ✅ | 插件 field type 的 value 仍存储为 JSONB |

所有新引入的架构决策（插件加载器、License 验证）将写入新的 ADR 系列（ADR-0006+）。
